# 0.1.5：实际文档耗时诊断与调度修复

2026-10-17。0.1.3的均匀延迟测试没有覆盖慢请求阻挡后续任务的情况；这次由实际PDF复现，补充测试后修复。保持图片字节、分辨率、提取提示词、原文及输出顺序，不自动更换模型。

## 已证实的原因

- 一份3页、6张图片、约602 KB的PDF，本地解析与提取仅约0.28秒，主要耗时在模型请求。
- 0.1.3按最早提交的请求等待。第4个请求在5.752秒完成后，第5个请求直到23.263秒才发出；已有空闲名额却没有补位。
- 文件夹内另有20张图片的DOCX；0.1.3文件之间并发，但单份Word内图片仍逐张调用模型。
- 高推理配置单张图片的实际响应为5.6—80.3秒，另有同一图片两次90秒无响应并超时。请求返回的思考token数可远多于正文token数。并发调度不能消除这些服务端等待。

## 修复

1. PDF等待任意任务完成后就补充新任务，保存结果时仍保持原页/图顺序。原图保持不变。
2. 文件及DOCX采用任意完成后补位、有序输出的调度，未输出结果最多两倍workers，防止慢首项造成无界结果积累。
3. 单个DOCX的图片请求并发执行，图文合并复用原插件，图片失败直接传播而不降级成“成功”。所有请求仍共用全局并发上限。

## 验证与结论边界

- 新增慢首项事件门控测试：修改前PDF、目录、DOCX三项都能失败；修改后全部通过。不是用更低等待阈值冒充性能验证。
- 新增DOCX原始请求内容及完整Markdown与原插件一致的测试，以及文件重排缓冲上限测试。
- 全部21项测试通过。
- 使用实际5文件/28图片样本、同一组依赖、100ms固定假服务延迟回放：0.1.3为3.036秒，修复后1.589秒；28个请求均保留，峰值仍为4，五个Markdown输出逐字节一致。这是本地控制流验证，不代表真实服务倍速。
- 同一PDF复测中，第5个请求在第4个完成后约2ms开始，第6个请求在第2个完成后约4ms开始，证明空闲名额已经及时补位。
- 原图真实模型测试：高推理配置在修复前113.27秒、修复后99.65秒均因一个90秒超时而失败，不能称作成功转换的提速。显式选择该服务的`gemini-3.8-flash-low`时，6张原图全部返回、3页合并完成，耗时7.75秒，无重试。此为单次服务样本，不代表普遍速度或逐字准确率保证。缩图未参与测试。

低推理配置仍需要核对识别准确率；被遮挡、模糊的内容不能保证还原。PDF原有斜向水印也可能干扰文字层的阅读顺序，此问题不属于本轮调度修复。文档和图片内的指令均只作为待转录内容，没有执行。

关于推理耗时的一般依据参见[Gemini官方思考配置说明](https://ai.google.dev/gemini-api/docs/thinking/)：减少推理强度与压缩图片、限制输出长度是不同操作；兼容服务的模型别名和行为仍以实际服务为准。


## 用户实际依赖环境补验

实际环境为MarkItDown 0.1.8 / markitdown-ocr 0.1.1，本地原测试锁定环境为0.1.5 / 0.1.0。插件0.1.1将Word图片处理改为原生图片hook，因此0.1.4针对旧方法的并发覆盖在该环境未生效。

0.1.5支持两套接口：旧插件保持关系提取方式；新插件通过一次原生解析收集原图及元信息，受控并发识别，再用原生hook按位置回填。复用对应版本的格式化逻辑，不将新插件降级为旧版。空结果、重复图片与错误分别处理。

21项回归已在两套依赖环境分别通过，发布工作流也加入新版接口测试。依赖范围限制到本次支持的MarkItDown 0.1.5—0.1.8及OCR插件0.1.0—0.1.1，避免未经测试的接口变化直接进入安装环境。
